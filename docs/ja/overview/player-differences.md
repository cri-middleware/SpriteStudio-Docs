# 🧩 プレイヤーごとの違い

すべての公式 Player は **同じコア** でアニメーションを評価します。したがって機能セットは
エンジンごとに作り直されるのではなく共有されており、その一覧は
[SDK コンセプト](../sdk/concepts.md) に掲載しています。それでも差が出るのは次の 2 点です。

1. **エンジンの描画層が再現できる範囲** - 特にブレンドモードは、ホストエンジンが提供する
   固定機能のブレンドステートへの割り当てになります。
2. **各 Player の実装がどこまで進んでいるか** - Player ごとに進捗が異なります。

このページで扱うのは、この **Player 間の差分** のみです。*すべての Player に共通* する制約
（シーク・逆再生の挙動、ブレンドの条件、ブラウザ要件、コアが状態計算のみを行い描画・再生は
Player に委ねている機能）は [共通の制限事項](../sdk/limitations.md) にまとめてあります。

## 🔍 ドキュメントに記載されている Player ごとの差分

| Player | 一言で言うと |
|---|---|
| **[Unity](../players/unity.md)** | uGUI（Canvas）パスにのみ、ワールドパスにはない制約がある |
| **[Web](../players/web.md)** | レンダラーに欠落はなく、フレームワーク連携の成熟度が異なる |
| **[Godot](../players/godot.md)** | 共通の制約を超える機能差はなし。Web 書き出しのみ追加要件 |
| **[Flutter](../players/flutter.md)** | 描画バックエンドが 2 種類。Canvas では 2 つのブレンドでバッチングが落ちる |
| **[Ren'Py](../players/renpy.md)** | Division・Overlay が `Mix` にフォールバック。一部機能は近似 |
| **[React Native](../players/react-native.md)** | マスク付きの Effect はマスクなしで描画、Mesh は対応済み。対応プラットフォームも狭い |
| **[wgpu](../players/wgpu.md)** | マスクのバックエンドが 2 つ。Bevy アダプタは自身の制限を 3 つ持つ |

!!! note "このページの読み方"
    以下の各節は、その Player 自身の **制約と適用範囲** ページに記載された内容の要約です。個別の
    ケースはリンク先を参照してください。このページはすべての Player が公開しています。
    したがって、ここに載っていない事項はその Player 自身の記述にもない、ということになります
    （対応の保証ではありません）。

    *すべての* Player に当てはまることは差分ではないため、ここではなく
    [共通の制限事項](../sdk/limitations.md) に記載しています。**テキストパーツと 9 スライス
    パーツがどの Player でもまだ描画されない**ことも、そちらに含まれます。

### Unity

**uGUI（Canvas）パス** は CanvasRenderer の「1 レンダラー = 1 メッシュ + 1 マテリアル」に
合わせるため、**単一アトラス前提**（他のアトラスのパーツは正しく参照できない）で、
**MIX / ADD のみ**対応し、それ以外のブレンドは `Mix` に集約されます。ワールドパスには
どちらの制約もありません。

`.ssqb` は**インポート**して参照できます。シーケンスとしての再生が未対応なのは Unity 固有
ではなく[全 Player 共通](../sdk/limitations.md)です。編集モードでは開始フレームの静止
プレビューのみが表示されます。

### Web

レンダラーパッケージ（`ssplayer-webgl`・`ssplayer-pixi`）自体に機能面の欠落はありません。
フレームワーク連携は成熟度が異なり、**RPG ツクール MZ は実験的（alpha）**（ピクチャの色調が
アニメーションに影響しない）、**TyranoScript・ティラノビルダー向けプラグインは beta** です。
ティラノビルダーはパーツ単位の色・表示切り替えと、アニメーションと話者の紐付けに対応する
コンポーネントがまだなく、これらは `[ss_*]` タグで記述します。

ブラウザ版コンバーター `ssconverter-web` は File System Access API を使うため
**Chromium 系ブラウザ限定**です。

### Godot

共通の制約を超える機能面の欠落はありません。GDExtension と カスタムモジュールの 2 形態で
提供され、**Web 書き出し** のみ追加要件があります（GDExtension には `dlink_enabled` 有効の
エンジンテンプレートが必要。カスタムモジュールでは不要）。また Web はシングルスレッド
（`nothread`）動作のため、COOP/COEP ヘッダーは不要です。

### Flutter

描画バックエンドが 2 種類（`flutter_gpu` / Canvas。Web は常に Canvas）。Canvas では
`Sub`・`Invert` を 3 パスで再現するためバッチングできません。`Div2`・`Overlay2` は
**両バックエンドとも** `Mix` として描画されます。

ウィジェットの**パーツトラッキング**は変換のみを転送し描画順は含まないため、追従した
ウィジェットはパーツの間ではなくアニメーション全体の手前に描画されます。ビューが等倍で
描画される前提でもあります。

### Ren'Py

Division・Overlay は `Mix` にフォールバックします。**パーツトラッキング**は変換のみを転送し
描画順は含まないため、追従した子はパーツの間ではなくスプライト全体の手前に描画されます。

マスク、メッシュパーツのパーツ全体の色、インスタンスパーツ *内部* に対する操作は、厳密では
なく近似的な挙動になります。個別の内容は Ren'Py 自身のドキュメントに列挙されています。

### React Native

**マスク付きのエフェクトはマスクなしで描画されます** - マスクの再現はアフィン変換された
1 枚のクアッドの UV を逆算してカバレッジを参照する方式で、エフェクトは 1 枚ではなくクアッドの
集合のため、切り抜くべき単一の形がないからです。**マスク付きのメッシュは対応済み**です。
メッシュは texcoord チャンネルをアトラスに使うため、独立したレイヤーへ描いたうえで、同じ
三角形に頂点ごとのカバレッジ UV を載せて `kDstIn` で重ね、レイヤーのアルファを切り抜きます。

また、外側からマスクが届いているフレームでは、**子が持つマスクの書き込みが無効**になります。

対応プラットフォームも狭く、tvOS・visionOS は Rust の Tier 3 ターゲット待ちで、Windows には
経路がありません。

### wgpu

`Div2`・`Overlay2` は `Mix` にフォールバックします。マスクには**バックエンドが 2 つあり、
ホストのパスが何を貸せるかで選ばれます**。**ステンシル**方式では INCR と INVERT が混在する
重なりが近似になり、入れ子は 8 ビット分に制限されます。**カバレッジビットマップ**方式は
ステンシルを貸せないパスのためのもので、累算がシェーダー変数になるため入れ子の制限は外れますが、
マスクを持つ Player 1 体につき描画パスが 1 つ増えます。どちらも止まる writer の予算は wgpu 固有
ではなく、[共通の制限事項](../sdk/limitations.md) にあります。

グループアルファは**パーツを 1 つずつ**合成するため、`0.5` の 2 パーツが重なった部分は `0.5`
ではなく `0.75` になります。13 種の連携シェーダーは **Normal パーツのみ**対応で、
`map0`・`map1` の副テクスチャや、マスクと併用したシェーダーパーツは対象外です。

**Bevy アダプタ**は別クレートで、Player 側ではなく Bevy のリリースラインに追従し、一度に
1 ラインだけを対象とします。Bevy の 2D デプステクスチャはステンシルを持たないためカバレッジ
方式が使われます。アダプタ自身が挙げている制限は 3 つで、**2 つ目のビューは警告付きで
スキップ**されること、**MSAA を off にする必要**があること（色を忠実に出すにはカメラに
`CompositingSpace::Srgb` も必要）、そして**ロードが同期的**で Bevy の `AssetServer` ではなく
ファイルシステムを直接読むため、ホットリロード・パックアセット・アトラス共有が効かないこと
です。

## 🎨 ブレンドモードで差が出やすい理由

SpriteStudio のブレンドは GPU のブレンドステートとして実現されるため、再現度はホストエンジンが
何を提供しているかに依存します。相当するモードがない場合、Player は失敗せずフォールバックします。
上記の差分が特定のモードに集中しているのはこのためです。

- **Division / Overlay** は参照実装の Player にも GPU ブレンドの対応がなく、`Mix` への
  フォールバックは実装が未完なのではなく意図的な挙動です。
- **Sub / Invert** には reverse-subtract または destination-replace のステートが必要です。それを
  持たないエンジンでも複数パスで厳密に再現できますが、バッチングは犠牲になります。つまり差は
  見た目ではなくパフォーマンスとして現れることがあります。

なお、Player 側に非がなくてもブレンドが意図どおりに見えない場合があります。描画先を参照する
モードは、下のピクセルが不透明であることを前提とするためです。これは全 Player 共通の性質で、
[共通の制限事項](../sdk/limitations.md) に記載しています。
