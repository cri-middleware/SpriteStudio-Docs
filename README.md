# SpriteStudio Docs

Documentation **portal** for the SpriteStudio SDK and its official players.

This repository is a lightweight hub. It does **not** re-host each player's docs - every
player keeps its own site in its own repository. This portal provides the unified entry
point and hosts the cross-cutting material that belongs to no single player:

- the landing page with product cards,
- the [ecosystem overview](docs/en/overview/ecosystem.md) and
  [platform chooser](docs/en/overview/choose-your-platform.md),
- the [asset-conversion overview](docs/en/overview/conversion.md) and the
  [standalone conversion tools](docs/en/overview/convert-with-a-standalone-tool.md),
- the [differences between players](docs/en/overview/player-differences.md) and the shared
  [runtime limitations](docs/en/sdk/limitations.md),
- shared [SDK concepts](docs/en/sdk/concepts.md), the [glossary](docs/en/sdk/glossary.md),
  the [format specification](docs/en/sdk/format-spec.md), and the
  [porting guide map](docs/en/sdk/porting.md),
- [support routing](docs/en/support.md) and shared licensing.

Publishes to: <https://cri-middleware.github.io/SpriteStudio-Docs/>

## Structure

```
docs/
  en/ , ja/          # one folder per locale, one config per locale
    assets/          # favicon (each locale ships its own copy)
    index.md         # landing page (product cards)
    overview/        # ecosystem, choose-your-platform, player-differences,
                     #   try-it, conversion, convert-with-a-standalone-tool,
                     #   motion-blending, ui-integration, runtime-changes,
                     #   ai-assistants
    sdk/             # concepts, glossary, format-spec, limitations, porting
                     #   (canonical, cross-player)
    players/         # thin entry pages that link out to each player's own docs
    support.md
    license.md
  requirements.txt
scripts/
  prepare-docs.{sh,ps1}       # create the venv, install the pinned toolchain
  build-docs.{sh,ps1}         # build both locales, strict, in the right order
  build-pages.{sh,ps1}        # the two above (serve=yes serves site/) - what the workflows run
  check-docs.py               # what --strict cannot see; build-docs runs it first
mkdocs.base.yml               # everything shared by both locales
mkdocs.yml                    # English  -> site/
mkdocs.ja.yml                 # Japanese -> site/ja/
.github/workflows/
  ci.yml                      # build (strict) on every pull request; weekly, external links too
  pages.yml                   # build (strict) + deploy via GitHub Pages, from main only
  provenance.yml              # ScanCode over the tracked files, before a publish
```

Every page exists in **both** `en/` and `ja/`, and each locale is built from its own config:
`mkdocs.yml` and `mkdocs.ja.yml` inherit the shared settings from `mkdocs.base.yml` and add
only what differs — the docs directory, the output directory, the site URL, the language,
and the navigation and the `llms.txt` index, each written in that language.

The site is generated by [Zensical](https://zensical.org), the successor to MkDocs +
Material for MkDocs from the same team. The configs remain valid MkDocs configs, so
`mkdocs-material` builds the same site if you need to compare engines.
