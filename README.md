# SpriteStudio-Docs

Documentation **portal** for the SpriteStudio SDK and its official players.

This repository is a lightweight hub. It does **not** re-host each player's docs - every
player keeps its own site in its own repository. This portal provides the unified entry
point and hosts the cross-cutting material that belongs to no single player:

- the landing page with product cards,
- the [ecosystem overview](docs/en/overview/ecosystem.md) and
  [platform chooser](docs/en/overview/choose-your-platform.md),
- the [asset-conversion overview](docs/en/overview/conversion.md) and the
  [standalone conversion tools](docs/en/overview/convert-with-a-standalone-tool.md),
- [feature support](docs/en/overview/feature-support.md) across players and the shared
  [runtime limitations](docs/en/sdk/limitations.md),
- shared [SDK concepts](docs/en/sdk/concepts.md), the [glossary](docs/en/sdk/glossary.md),
  the [format specification](docs/en/sdk/format-spec.md), and the
  [porting guide map](docs/en/sdk/porting.md),
- [support routing](docs/en/support.md) and shared licensing.

Published at: <https://cri-middleware.github.io/SpriteStudio-Docs/>

## Structure

```
docs/
  en/ , ja/          # one folder per locale, one config per locale
    assets/          # favicon (each locale ships its own copy)
    index.md         # landing page (product cards)
    overview/        # ecosystem, choose-your-platform, feature-support,
                     #   try-it, conversion, convert-with-a-standalone-tool
    sdk/             # concepts, glossary, format-spec, limitations, porting
                     #   (canonical, cross-player)
    players/         # thin entry pages that link out to each player's own docs
    support.md
    license.md
  requirements.txt
scripts/
  prepare.{sh,ps1}            # create the venv, install the pinned toolchain
  build.{sh,ps1}              # build both locales, strict, in the right order
mkdocs.base.yml               # everything shared by both locales
mkdocs.yml                    # English  -> site/
mkdocs.ja.yml                 # Japanese -> site/ja/
.github/workflows/pages.yml   # build (strict) + deploy via GitHub Pages
```

Every page exists in **both** `en/` and `ja/`, and each locale is built from its own config:
`mkdocs.yml` and `mkdocs.ja.yml` inherit the shared settings from `mkdocs.base.yml` and add
only what differs — the docs directory, the output directory, the site URL, the language,
and the navigation with its labels in that language.

The site is generated by [Zensical](https://zensical.org), the successor to MkDocs +
Material for MkDocs from the same team. The configs remain valid MkDocs configs, so
`mkdocs-material` builds the same site if you need to compare engines.

## Local development

`mkdocs.base.yml` sets `strict: true`, so the build commands below fail on a broken internal
link — no flag required, though `--strict` is spelled out everywhere as a reminder.
**Nothing builds the docs on a pull request** — `pages.yml` runs on `workflow_dispatch`
alone — so running the build locally is the only gate.

Build the English site first: the Japanese one is written into `site/ja`, and the English
build clears `site/` on its way in — which leaves no Japanese site at all, not a stale one.
Two scripts take care of the setup and that order:

```bash
scripts/prepare-docs.sh     # create .venv and install docs/requirements.txt
scripts/build-docs.sh       # English, then Japanese, both --strict
```

```powershell
scripts\prepare-docs.ps1    # the PowerShell twins; same options, same output
scripts\build-docs.ps1
```

Both take `key=value` options and `--help`, like the scripts in the player repositories:

| | |
|---|---|
| `prepare-docs.sh python=<exe>` | interpreter to build the venv with (`python3`; `py` for the `.ps1`) |
| `prepare-docs.sh venv=<dir>` | where the virtualenv goes (`.venv`) |
| `prepare-docs.sh force=yes` | delete the venv and recreate it, for one that has gone wrong |
| `build-docs.sh locale=<all\|en\|ja>` | which locale to build (`all` — the order above) |
| `build-docs.sh venv=<dir>` | virtualenv to run `zensical` from; falls back to `PATH` |

`build-docs.sh locale=en` on its own is the one to watch: it removes `site/ja`, and says so.

### Running the tools directly

Nothing is hidden behind the scripts — this is all they run:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r docs/requirements.txt

.venv/bin/zensical build --strict               # the only gate; nothing checks a PR
.venv/bin/zensical build -f mkdocs.ja.yml --strict
```

```powershell
py -m venv .venv
.\.venv\Scripts\python -m pip install -r docs/requirements.txt

.\.venv\Scripts\zensical build --strict         # the only gate; nothing checks a PR
.\.venv\Scripts\zensical build -f mkdocs.ja.yml --strict
```

### Previewing while you write

`serve` has no script, because it validates nothing and serves one locale at a time:

```bash
.venv/bin/zensical serve                        # preview English at http://127.0.0.1:8000
.venv/bin/zensical serve -f mkdocs.ja.yml       # preview Japanese (stop the other one first)
```

```powershell
.\.venv\Scripts\zensical serve                  # preview English at http://127.0.0.1:8000
.\.venv\Scripts\zensical serve -f mkdocs.ja.yml # preview Japanese (stop the other one first)
```

`zensical serve --strict` is accepted but currently does nothing, so run
`scripts/build-docs.sh` before you push.

### Previewing the language selector

`serve` renders one locale at a time, so the other language does not exist under it and the
selector 404s. Build both locales instead and serve the result:

```bash
scripts/build-docs.sh

python3 -m http.server 8000 -d site
```

The selector links are relative and per page, so switching language from, say,
`/sdk/concepts/` lands on `/ja/sdk/concepts/` rather than the Japanese home page — and it
works at any path prefix, including this one.
